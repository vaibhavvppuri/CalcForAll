# Numeric work and allocation budgets

CalcForAll keeps rational arithmetic exact and irrational arithmetic in BigDecimal. It deliberately refuses calculations that exceed a fixed work or allocation budget. Refusal is an ordinary typed error, not infinity, a fabricated zero, or a device-dependent timeout.

| Boundary | Budget |
| --- | --- |
| Expression input | 65,536 characters in the core; app/API may be stricter |
| Individual literal | 10,000 digits; decimal scale between −20,000 and 20,000 |
| Rational numerator and denominator | 131,072 bits each after reduction |
| Rational addition/comparison scratch values | At most 262,145 bits |
| Session compute precision | 5–50 digits, at least four more than display precision |
| Direct numeric kernel precision | Up to 1,024 digits plus bounded internal guard digits |
| Decimal value | Adjusted exponent within ±32,768, scale within ±65,536 |
| Integer powers, real and complex | Absolute exponent at most 1,000,000; result size still bounded |
| Factorial | Argument at most 10,000 |
| Permutations/combinations | At most 10,000 product terms; result size still bounded |
| General transcendental input | Adjusted exponent within ±10,000 |
| Exponential and hyperbolic argument | Absolute value at most 10,000 |
| General non-symbolic trig argument | Absolute value at most 1,000,000 radians |
| Trial square-factor extraction | Divisors through 4,096, plus a whole-number perfect-square check |
| Widest expansion of a surd or a multiple of π or e | 1,144 digits: comparison, whole part, fractional part, remainder, and a difference of two exact values |

Input budgets are checked before converting strings or expanding decimal scales into large integers. Rational multiplication and division cross-cancel before multiplying. Addition uses the shared denominator and cancels before constructing the final denominator. Integer multiplication checks operand bit lengths before allocation. Square roots reduce numerator and denominator separately, so a large perfect-square fraction can still have a small exact root. Exact integer root detection uses integer Newton iteration; a huge root index takes work independent of that index, using guarded `exp(log(x)/n)` when no exact root exists.

Session precision is capped at 50 digits because mixed arithmetic still computes its nominal result in a 50-significant-digit context. The app and API expose at most 32 displayed significant digits; the lower-level Settings type permits up to 46 with four guard digits. Direct kernel calls can request more precision within the allocation budget. A precision setting is a work budget, not a guarantee that every displayed digit is correct after cancellation. Exact rational, surd and symbolic-constant forms remain exact until an operation needs a decimal representation.

## Decimal estimates and error bounds

A decimal estimate carries a nominal `BigDecimal` value and an optional nonnegative `absoluteError`. A supplied error establishes the closed interval `[value − absoluteError, value + absoluteError]`; a missing error means the uncertainty is unknown. An error of zero denotes a known point while retaining approximate provenance. Unknown does not mean zero. The interval is a deterministic arithmetic enclosure, not a confidence interval or a claim about measurement precision.

Exact rational arithmetic remains independent of this metadata. Decimal addition, subtraction, multiplication and division propagate available intervals with directed rounding and include the distance between the computed nominal value and the enclosure. Unknown input uncertainty propagates as unknown. Division refuses an established denominator interval containing zero. Dependencies between repeated uses of a quantity are not tracked, so intervals can be wider than the tight mathematical range. Exact algebraic paths may still establish identities such as an exact-zero product.

For example, `10^49+sqrt(2)-10^49` can have nominal value 1 at the working precision, but its attached interval includes the lost fraction; the display exposes the material uncertainty with `±`. Its floor is refused because that interval crosses an integer. `(10^49+1)-10^49` stays exactly 1. A completely discarded nonzero addend is still refused by the existing allocation/precision guard. Differences between two exact forms can widen their expansions within the 1,144-digit limit; this does not create additional information in an already stored estimate.

The reusable expression format is `approx(value)` for an unknown estimate and `approx(value,error)` for a bounded estimate. The latter adds any uncertainty already present in its first argument; it cannot replace unknown uncertainty with an asserted bound. `Formatter.reusableInput` preserves this information for scalar, complex and unit values. The legacy `Formatter.input` remains a numeric/text representation without the error metadata and is unsuitable on its own for preserving an estimate across calculator input. Registers and `Ans` retain the original numeric object, including its error bound. Session expressions that contain `approx` retain the explicit contract on re-evaluation.

A bounded estimate's radius is shown when it affects the displayed resolution; the displayed radius is rounded upward. An estimate with unknown uncertainty retains the approximate marker supplied by the result presentation. A complex coefficient whose interval crosses zero is rendered with its signed coefficient in parentheses, so its possible negative and positive values are not lost by separating sign and magnitude.

## Established elementary enclosures

`DecimalBounds` uses outward-rounded decimal arithmetic. Square-root endpoints are verified by exact squaring. Bounds for π use the Machin formula with alternating-series remainders; bounds for e use the factorial series and an explicit tail bound. `CertifiedMath` bounds exp, ln, sin, cos, tan and the forward hyperbolic functions through range reduction, directed arithmetic and explicit Taylor/geometric remainders. Trigonometric argument reduction includes the uncertainty in π, and sin/cos propagate input uncertainty using their global derivative bound. Inverse trigonometric and hyperbolic functions also have established real enclosures: atan uses half-angle reduction and an alternating-series remainder; asin/acos and inverse hyperbolic functions compose monotone identities with directed sqrt/log bounds. atan2 encloses a rectangle only when it avoids the origin and principal-angle branch cut. Supported positive-base real powers and general real roots compose these kernels. A domain crossing or exhausted bound budget returns a typed refusal.

These are arithmetic enclosures derived from the formulas and remainder bounds; agreement between computations at two precisions is not used as a proof. Independent reference-value tests and boundary tests supplement the derivation but do not turn unverified sampling methods into certified algorithms.

Rounding, truncation, fractional part and remainder may return a discrete result only when every point in the established input interval gives the same required integer. `sign` similarly needs a fixed sign, and min/max enclose the endpoint-wise extrema. An unknown bound or an interval crossing a decision boundary gives a typed unsupported result rather than snapping to the nearby integer. Ordinary cases such as `floor(sin(1))`, `floor(log10(12))` and `ceil(exp(1))` have adequate bounds. Cases such as `floor(tanh(60))` can remain unsupported at this precision because the returned enclosure reaches 1. A nominal zero or integer with nonzero/unknown uncertainty cannot take an exact zero, integer-exponent, factorial or exact-angle shortcut. Odd roots handle a nominal zero directly and propagate established endpoint bounds across zero; an unknown nominal zero remains unknown rather than taking log(0) or becoming an exact zero. Even-root intervals that include negative values are refused. A nominal square-root estimate with unknown input uncertainty supplies no established domain or exact-zero proof. A rounding call evaluates its argument once at the maximum 50-digit session precision; it does not compare multiple evaluations or reinterpret a stored estimate as more accurate. Known-point decimal rounding uses all digits actually stored.

Not every numerical algorithm has an established enclosure. Generic numerical integrations and derivatives, sampled limits, numeric complex roots, curve-fit estimates and other legacy decimal producers may still carry unknown uncertainty. Their approximate output can be displayed and reused as an estimate, but cannot establish a later rounding decision. Financial tools currently require known point inputs; they do not accept an uncertain rate as exact zero. Integer-period finance growth uses paired power/sum recurrences so a tiny nonzero rate is not lost by subtracting 1 from an already rounded power.

## Equations, roots and ordered tools

Equation verdicts compare exact quantities exactly, or use established intervals: disjoint intervals prove inequality; overlapping or unknown intervals are undecided. Equal nominal digits do not prove equality. Comparing one stored quantity with itself remains a valid identity. A bounded set of domain-checked written identities can establish exact results (for example sin(x)^2+cos(x)^2, matched inverse pairs, and cancellation of a proved nonzero repeated factor). Names remain case-sensitive and independent approx constructors are never treated as one shared uncertain quantity. General algebraic identities outside this set can remain undecided. Exact constant rewrites do not erase an unknown function-domain uncertainty; direct subtraction of the same real register remains a valid correlation. Identity rules read completed AST-node values from one evaluation, including intermediate binary-spine nodes, rather than recursively evaluating their arguments again. The memo is cleared before each public evaluation so changed registers or graph bindings cannot reuse stale values. Quadratic discriminants, system determinants and matrix pivots need a definite established sign; an interval containing zero cannot be declared a repeated root or a singular system. Matrix elimination may use another row with a proved nonzero pivot before refusing. Exact elimination identities set the eliminated pivot column to zero without pretending that unrelated interval quantities are equal.

Higher-degree polynomial solving now requires exact rational coefficients after exact common-factor cancellation. After the original expression is established to be a polynomial within the degree limit, explicitly written products can be solved factor by factor. Powers of the unknown and positive integer powers such as `(x-e)^2=0` retain their bases, without losing the repeated-factor dependency. This supports products containing separately solvable irrational linear/quadratic factors without inventing rational coefficients. Other uncertain or irrational coefficients receive an explicit unsupported explanation. Rounded coefficient samples are not substituted for the original polynomial, and nearby roots are not merged by a tolerance. Real roots isolated with exact rational Sturm arithmetic retain their enclosing bracket as an error bound; numerical complex-root residual checks still produce estimates with unknown uncertainty.

Each higher-degree polynomial solve has a **10-second cooperative wall-clock budget**. The allowance was increased from three seconds after the ordinary quintic `x^5-x-1=0` exhausted that limit on the API 34 emulator. Degree 8, coefficient-size and normalized-size caps, rational-candidate limits, isolation/refinement/complex-iteration caps, and all root-acceptance checks remain unchanged. Expiry returns an explicit unsupported result naming the time budget, never a partial root list. This allows slower arithmetic more time; it does not relax accuracy or promise completion on every device. Checks occur between bounded operations, so one arithmetic operation is not forcibly interrupted. Re-solving history can incur the budget again for each polynomial entry.

Descriptive statistics, quartiles/modes and regression currently require known point observations. They refuse unknown or nonzero-bound observations instead of sorting nominal values and attaching a misleadingly narrow minimum, median or mode. Exact rational observations and explicitly known-point decimal observations remain supported. These are documented analysis limits, not an assertion that every mathematical expression has an available certified implementation.

Real and complex integer powers share the exponent budget. Rational powers take an exact root first when possible; half-integer powers preserve rational/surd forms. Otherwise they evaluate the bounded logarithmic product using the exponent ratio directly, avoiding an enormous `base^numerator` temporary for a moderate fraction. Negative bases retain the real odd-root convention. General real powers check the logarithmic product before calling the exponential kernel. Exact standard angles retain their symbolic reduction, including enormous exact multiples of π; a non-symbolic argument above the trig budget reports overflow instead of attempting unreliable argument reduction. Square-factor extraction may leave a larger square factor inside a radical: its value remains exact, but its written form may not be fully reduced.

These limits protect the numeric layer. They do not promise a universal wall-clock deadline for every legal expression, and callers should also bound batch sizes and AST depth. The API and app impose their own smaller input limits and run calculations away from the UI thread. Tests cover ordinary scientific notation beyond binary64 (`1e±309`), 1,800-term sums, billion-index roots, cross-cancellation of large rationals, exact combinatorics, and typed refusals at the boundaries.

Main-entry equation and system routing has an additional iterative preflight before recursive unknown discovery and polynomial extraction: at most 512 expression nodes in total across both sides of every equation, with AST depth at most 64. Exceeding either limit returns a typed unsupported error asking for a simpler expression. This also catches long left-associated sums whose AST is deep despite having few parentheses. Plain scalar evaluation retains its separate iterative long-sum path; the equation limit does not impose a new 512-node cap on direct core scalar calculations. The API independently applies its advertised 512-node/depth-64 request limit to all expressions. Graph root/intersection analysis has its own structural and work budgets described below.

The history tape holds at most 5,000 entries, 90,000 total editor nodes, 16,384 nodes per calculation, and nesting depth 128. Reaching a limit rejects the new operation explicitly; it never silently discards history. The last 100 whole transactions can be undone. Dependency analysis uses iterative strongly connected components and topological ordering, avoiding recursion and per-row transitive reachability tables. Rejected edits leave the current tape, undo/redo history, and next entry identifier unchanged. The durable session codec has a separate total limit that also includes the current editor.

Regression uses centered sums to preserve small variation in large-offset data. A constant response still gives its valid horizontal fitted line, while Pearson correlation and the coefficient of determination are explicitly undefined (`null`). Constant predictor values remain a typed domain error.

Graph root/intersection analysis accepts 2–4,096 samples and checks an iterative 512-node, 64-depth expression budget before recursive polynomial extraction. A shared `RootSearchOptions` budget covers scanning, bisection and final candidate verification: 10,000 evaluations and 5 seconds by default, with hard caps of 20,000 evaluations and 15 seconds. Its optional `shouldStop` callback and thread interruption are checked around operations. Existing calculator and root-finder calls remain valid without options. An individual bounded arithmetic/extraction call cannot be preempted halfway through its work.

An exhausted or cancelled search returns a typed unsupported failure, never partial roots labelled as a complete search. Uncomputed samples also make the search incomplete. Intersections require equal settings and equal memory bindings for both functions; the API refuses mismatched contexts rather than evaluating the second curve under the first curve's memory.

Numeric graph roots are residual-checked candidates under continuity assumptions, not exact roots or a proof that every root was found. Sample signs must follow from established bounds; residual checks use the upper bound on the candidate residual and lower bounds on the original endpoint magnitudes. Unknown error or a sign-crossing sample can make the analysis unsupported. A numeric sign bracket must shrink to width at most `1e-12`; endpoint-based acceptance requires both current endpoint residual bounds to decrease by a factor of at least `1e6` relative to their respective original endpoint lower magnitudes. The selected endpoint must pass both absolute residual `1e-6` and `1e-6` times the smaller original endpoint lower magnitude. Alternatively, a midpoint whose established interval includes zero may pass that same residual upper-bound test once the bracket is sufficiently narrow, without choosing a half-bracket from its nominal sign. Final substitution repeats that candidate-specific check. Refinement continues beyond the width threshold when residual evidence is insufficient, subject to the same time/evaluation/120-bisection limits. Tiny continuous roots, including `1e-300*sin(x-0.1234567)` and `1e-300*(x^3-2)`, remain supported.

No finite sample rule establishes continuity for an arbitrary expression. For example, `(x-0.1234567)^2/(x-0.1234567)` agrees with a line except at a removable hole at that line's only root. Likewise `(x-p)*ln(abs(x-p))` has a zero limit at an undefined point. This release explicitly refuses these numeric root searches before sampling rather than presenting a hole as a root.

The numeric analysis subset permits addition, subtraction, multiplication, division by a closed nonzero real constant, variable bases raised to fixed nonnegative integer powers, and positive closed bases raised to supported variable expressions. Supported dependent functions are `sin`, `cos`, `atan`, `abs`, `cbrt`, `exp`, `sinh`, `cosh`, `tanh`, `asinh`, `hypot`, `min`, and `max`, including their registered aliases. Constants use the curve's own settings and memory and consume the shared evaluation budget. Variable-dependent denominators/negative or fractional powers, restricted-domain functions such as `ln`, `sqrt`, `tan`, `asin`, and discontinuous operations such as floor, sign, and factorial receive an explicit unsupported-analysis explanation. Closed subexpressions can contain those functions when they evaluate successfully. Curve plotting and point tracing remain available; exact low-degree polynomial solving follows its existing path. This is a limited continuity-safe syntax subset, not a general symbolic or interval domain prover.

Physical constants were checked against the [NIST complete 2022 CODATA table](https://physics.nist.gov/cuu/Constants/Table/allascii.txt) on 10 November 2026. Electron mass is `9.1093837139e-31 kg` with standard uncertainty `2.8e-40 kg`; proton mass is `1.67262192595e-27 kg` with uncertainty `5.2e-37 kg`. The molar gas constant stores the full exact SI product `NA × k_B = 8.31446261815324 J/(mol·K)`. Measured constants remain labelled with nonzero uncertainty.

## Numerical limits remain estimates

Sampled one-sided limits compare successive values relative to their own scale, without a unit-sized tolerance floor. A small nonzero constant such as `1e-20` is not replaced by zero. Two one-sided estimates must agree when rounded to their shared reported significant digits before a two-sided estimate is shown; a small jump is still a jump. Zero is used only where a supported continuity/degree check supplies that specific conclusion, never merely because the sampled magnitude is small. The reported estimate and its agreement digits remain sampling evidence, with unknown arithmetic error metadata; they are not a rigorous limit certificate or an uncertainty enclosure.
